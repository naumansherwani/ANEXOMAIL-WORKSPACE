## J7 — 5G Slice-on-Demand (CAMARA Quality on Demand)
Real: CAMARA QoD lets an app ask the operator for a priority/latency profile for one device and flow over REST; the app gets a session id and a webhook (`NETWORK_TERMINATED` if the network can no longer keep the profile). Live at Elisa and Hrvatski Telekom (Nokia Network as Code), T-Mobile US (5G SA, DevEdge); Verizon in development; AT&T/T-Mobile/Verizon via the Aduna venture (roadmap); Telefonica Open Gateway; Azure Programmable Connectivity. Source: [privatelteand5g.com QoD article](https://www.privatelteand5g.com/camara-and-the-quality-on-demand-api-real-world-use-cases-for-dedicated-latency/), [GSMA Open Gateway](https://www.gsma.com/solutions-and-impact/gsma-open-gateway/).
NOT real: "absolute 0% drop". QoD asks for priority; the operator may refuse or end it. Jazz/Telenor (Pakistan): I found NO source that they sell QoD. It needs a commercial agreement (direct or an aggregator) and the user's consent to identify the device/number.
Build (when the order comes): `qod` trait in Rust with a provider adapter per aggregator; SQL session ledger (hash-chained, same pattern as E140); the app asks QoD only for a call or sync the user started; status says "not available on your network" when no provider covers the number. Never a fake "VIP slice active".

## J8 — NIDD (Non-IP Data Delivery) for T3 cancel / alert / wipe
Real: NIDD is part of Cellular IoT optimisation. An application server reaches a device through the operator's SCEF (4G) / NEF (5G) REST API `3gpp-nidd/v1` (create configuration, send downlink data) and the device holds a Non-IP PDN. Source: [Oracle SCEF NIDD](https://docs.oracle.com/cd/F27846_01/docs.85/SCEF/nidd.html).
NOT real for phones: the same source says smartphone apps use normal IP PDN connections and do not use NIDD. A phone app cannot receive NIDD, and our server cannot talk "to the towers"; only an operator exposes SCEF/NEF, and only to IoT-class devices. So NIDD cannot be the phone's kill channel.
What we build instead (genuinely works with the data network OFF on the attacker's side): a **dead-man vault lease**. The device vault key (AnexoChat local database, mail cache) needs a short server-signed lease (kernel-verified Ed25519, e.g. 15 min, renewable only while the device is approved). Revoke a device = the lease is not renewed = the vault locks itself when the lease ends, no connectivity needed from us, and a phone that is kept offline by the thief locks too. Fast path while it IS online: J6 push + WebTransport revoke. NIDD stays a documented option only for a future Anexo IoT hardware token (CIoT modem).
Founder: J8 = lease + fast revoke now; NIDD adapter only if an operator offers SCEF/NEF access AND an IoT-class device exists.

## J9 — eSIM cryptographic vault binding (GSMA IoT SAFE / ARA-M)
Real: IoT SAFE is a GSMA standard where a SIM applet is the root of trust for cellular IoT devices; the device reaches it through a middleware library and AT+CSIM over the modem's ISO7816 interface; the SIM/connectivity provider provisions it. Source: [emnify on IoT SAFE](https://www.emnify.com/blog/iot-safe) (vendor article). On Android, an app can use SIM applets only if the SIM's access rules (ARA-M) allow the app's signing certificate, which the operator/issuer controls.
NOT real: a third party cannot "push a custom applet" onto a normal user's eSIM; the profile belongs to the operator. iOS exposes no SIM-applet access to apps. "Mathematically 0%" is not a claim anyone can make.
What we build: (1) keep J3 passkeys as the device-bound root (hardware attestation, AAGUID allow-list, MDS, Secure Enclave/StrongBox through WebAuthn); (2) add **SIM-change risk signals** through CAMARA SIM Swap / Device Swap / Number Verification (same Open Gateway family, operator coverage again unverified in Pakistan) into the E139 risk engine as an extra reason, never a login factor; (3) an IoT SAFE adapter only for a future Anexo hardware token or an enterprise that supplies its own IoT SAFE SIMs.
