| [RFC 9162 §2.1.4](https://datatracker.ietf.org/doc/rfc9162/) Merkle consistency proofs | Proof that tree size *n* extends tree size *m* without changing any of the first *m* leaves. Proof = at most ceil(log2 n)+1 hashes. Verifier keeps `fn/sn` (positions) and `fr/sr` (rebuilt old/new root); accept only if `fr`=old root, `sr`=new root, `sn`=0. | [C2SP tlog-cosignature](https://www.github.com/C2SP/C2SP/blob/main/tlog-cosignature.md) | A WITNESS is a cosigner that keeps the latest tree head it saw per log and cosigns only after checking a consistency proof. Algorithms: **Ed25519** (cosignature/v1: `time`, origin, size, base64 root) and **ML-DSA-44** (post-quantum, the spec says recommended for NEW deployments). Clients are configured with (cosigner name, algorithm, public key) and verify a quorum. |

## The design (four layers, each closes one limit)
| Part | What | Technology | Closes |

| **G5a** | **Consistency proofs.** SQL `founder_audit_consistency_proof(old_size, new_size)` generates the RFC 9162 SUBPROOF over the existing E107 tree. One Rust source `server/rust/merkle_core.rs` gets `verify_consistency` (the ONE shared code, Rule 52). Kernel `merkle@2` exports `consistency_verify`. | **G5b** | **Signed checkpoints in the C2SP format.** Each seal is published as a standard checkpoint note signed by a dedicated audit-log key (its own Ed25519 key, NOT the transport signing key; ML-DSA-44 option decided in G5-0 after a crate licence/audit read, since `ring` has none). Key id per the spec. | Rust + SQL | prepares limit 2 (a standard object others can cosign) |
| **G5c** | **External witnesses.** After each seal, Rust sends the checkpoint plus the consistency proof to independent witnesses (C2SP witness protocol); a witness checks it against what it saw before and returns a cosignature. Cosignatures are stored in SQL and shown. The browser verifies **k of n** witness cosignatures in WASM against witness keys pinned INSIDE the kernel release (so the server cannot swap them). ## Review gate (the founder's "review kero jab tak super advance na ho")
A part is NOT done until all of these are shown, in this order:
1. **Exhaustive vectors:** every pair (m, n) with 1 <= m <= n <= 150: SQL proof == Rust proof, and the verifier accepts. Reference generator written from RFC 9162 in a separate language (Python) so one bug cannot hide in two copies.
2. **Negative tests:** flipping any single bit of any proof hash, swapping hash order, truncating or extending the proof, wrong sizes (m=0, m>n), wrong old/new root: each MUST be rejected.
3. **Three-way parity:** SQL = Rust = WASM kernel on the same vectors (the same method E107 used for inclusion proofs).
4. **Property/fuzz test** on random trees and random byte garbage into the verifier (never panics, never accepts).
5. **Independent review:** a second reviewer that did not write the code reads the diff against this file and the RFC and reports. Findings are fixed and the review repeated until it reports none.
6. Then the server run and the founder's Chrome check. GREEN only with the pasted proof.

**Design fact found while testing (written so it is never forgotten):** a Merkle root does not commit to its own tree size. Verifying a proof "for size n+1" against the root of size n can pass when the proof's last element is the leaf hash. So the SIZES must be bound by something signed: the E107 seal already hashes `(id, upto_seq, leaves, root, head_hash)` into `cp_hash`, and G5b signs that as a C2SP checkpoint. The consistency check is only ever used together with a seal/checkpoint that fixes the size.

## G5b — C2SP signed checkpoints (founder 2 Nov 06:02 "shuru kero, advance codes, new sql advance level"; status: IN PROGRESS)
**Technology read (real sources, 2 Nov 06:05):** C2SP `signed-note` (note text ends in `\n`, blank line, `— <name> <base64(4-byte key ID || signature)>` lines; key name non-empty, no Unicode spaces, no `+`; Ed25519 key ID = first 4 bytes of SHA-256(name ‖ 0x0A ‖ 0x01 ‖ 32-byte pubkey); the signature covers the note text including its final newline; canonical base64 only; unknown keys ignored, a known key with a bad signature rejects the note; at least 16 signatures accepted) and `tlog-checkpoint` (line 1 origin, line 2 tree size in decimal without leading zeros, line 3 RFC 6962 root in standard padded base64, extension lines NOT recommended; an Ed25519 log signature key name SHOULD be the log origin). Independent oracle on this machine: Go's own `note` package (GOROOT `cmd/vendor/golang.org/x/mod/sumdb/note`) with its published example (key `PeterNeumann`, ID `c74f20a3`).
**Design:** (1) Rust core `server/rust/checkpoint_core.rs` (pure: strict canonical base64, key ID, body, strict note parser, verifier with a caller-supplied Ed25519 closure) shared with the kernel by `#[path]`. (2) Own audit-log key (NOT the s1 response key): `founder-auditlog.p8` 0400, public key in the SQL registry, origin = key name = `founderworkspace.anexomail.com/audit-log`. (3) SQL E123: registry with exactly one active key, retired keys stay forever (old notes keep verifying), `founder_audit_signed_checkpoints` append-only; a trigger recomputes the expected note body from the seal row, so a note whose size/root differ from the seal can not be stored; Ed25519 itself is verified by Rust before the door is called and by the kernel in the browser (SQL has no Ed25519). (4) Rust tick signs every seal that has no signed note (never a size without a seal, never two different notes for one size). (5) Kernel `checkpoint@1` (0.8.0): `checkpoint_verify(note, name, pubkey, size, root)`: all parsing and crypto in the kernel, none in the UI (Rule 70). (6) UI: Ledger seal row says "signed by the audit-log key" or a clear warning; the public key is pinned TOFU in the browser like the seal pin (a changed key is a loud warning, never silent).
**Honest limits (never over-claimed):** a signature by a key that lives on the same server proves "this server said so", not "an outside party saw it" (that is G5c time anchors). A fully compromised server can sign anything with the key; the signed checkpoint binds the SIZE to the root (closing the G5a gap), and key rotation is explicit and audited.
**Review gate:** Go oracle vectors (Go signs, Rust verifies; Rust signs from the same seed, bytes identical), the published PeterNeumann vector, every single-byte flip of a signed note rejected, strict-format negatives, SQL selftest, real wasm test, independent reviewer repeated until clean.
