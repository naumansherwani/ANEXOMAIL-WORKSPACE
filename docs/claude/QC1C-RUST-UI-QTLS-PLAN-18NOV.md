## RUST (17 features)
- F2-3 probe core: new file server/founder/src/fmail_tls.rs, `pub async fn probe_domain(res, domain) -> ProbeResult`. It takes a DOMAIN only (F2-5): the caller strips an address with mime::domain_of; a test proves a string with '@' is refused. Hosts come from fmail_smtp::targets (F4-1/2/3 reuse), at most 3 distinct MX hosts are contacted (small footprint), tried in priority order until one answers its SMTP greeting.
- F2-4 conversation: 220 greeting (10 s), EHLO with the same helo name the sender uses (mail.anexomail.com), look for STARTTLS in the EHLO lines, STARTTLS, handshake, QUIT. `fn never_mail_from` is a test that the byte stream sent never contains MAIL / RCPT / DATA. The connection closes within about 2 s after the handshake. No mail, no address, one short log line at their side.
- F4-5 timeouts: 10 s connect, 10 s per command, 45 s cap for the whole probe (tarpit defence); a slow server becomes `unreachable` with the reason "greeting timed out".
- F4-6 handshake: TLS 1.3 and 1.2 allowed (so a 1.2-only server is classified classic12, not failed), key exchange offered X25519MLKEM768 first, then X25519, P-256, P-384; ring provider + rustls-post-quantum exactly like RustlsUpgrade.
- F4-7 certificate: pass 1 verifies against the MX host name with the webpki roots. If pass 1 fails with a certificate error, pass 2 repeats the handshake with a no-verify verifier ONLY to read the group and version (nothing is sent but QUIT); cert_verified = false is stored and shown. Opportunistic TLS (RFC 7435) accepts unverified certificates between MTAs, so unverified is a fact to display, not a failure.
- Verdict mapping (closed list, no unknown): TLS 1.3 + a group containing MLKEM = pq; TLS 1.3 otherwise = classic13; TLS 1.2 or older = classic12; EHLO without STARTTLS = none; STARTTLS answered not 220 or both handshake passes failed = refused; no host gave a greeting = unreachable (a reason per host); null MX, or no MX and no address = nomail; a name that points only to private addresses = unreachable with the reason "private address, not contacted".
- F4-8 `hosts_tried`: every contacted host with its own result goes into the sealed detail JSON (E189 detail_sealed); the verdict is the best-priority host that answered.
- F7-8 doors (fmail_tls.rs + main.rs route): GET /founder/v1/mail/tls?box=&domains=a.com,b.org (max 50): read only, computes the blinds with the existing blind helper of fmail_book, calls fmail_dtls_get189, signed answer the kernel verifies. POST /founder/v1/mail/tls/check {box, domains}: signed like /mail/release; for each domain claim189 -> spawn a probe task -> finish189; returns the current rows (checking where in flight). Rate limit comes from claim189 (30 per hour) plus a per-request cap of 10 domains.
- F3-4 retry worker: a tokio interval (30 s) over fmail_dtls_due189; opens the sealed name (fmail_seal, AAD = mailbox|blind), claim, probe, finish; global semaphore of 4 probes, jitter of up to 5 s; stops by itself when attempts reach 4 (SQL decides).
- F3-5 + F3-6 chip updates by itself: SQL E190 (E188 pattern) widens the E187 kind list with 'tls' and adds a trigger on fmail_domain_tls189 that writes one 'tls' line (ids only); the browser already refreshes on every kind, so the chip changes through QLIVE with no refresh and no new transport.
- F1-3 delivered mail: fmail_smtp's Upgrade returns a TlsFact {verdict, group, version, cipher}; fmail_out writes it per recipient domain through fmail_dtls_real189 (source sent) after a delivered result; the recipient address is never sent to SQL, only the blind + sealed domain.
- F5-2 proof: the same call returns predicted + mismatch; when mismatch, a plain line goes to the outbox note ("we expected post-quantum, delivery used classic TLS").
- F1-4 received mail: the Postfix Received header (already parsed in Q1b4) names a TLS version but no key-exchange group, so a TLS 1.3 header proves nothing about pq. Decision (disclosed): a weak hint is written ONLY when the header proves TLS 1.2 or older or no TLS; for TLS 1.3 nothing is written.

## QTLS (4 features, started on his order 08:18; shares the E189 / fmail_tls plumbing but is its own file fmail_qtls.rs)
- F8-1 MTA-STS (RFC 8461): TXT `_mta-sts.<domain>` (mail-auth MtaSts parser) then HTTPS GET https://mta-sts.<domain>/.well-known/mta-sts.txt (certificate must validate, no redirects, small size cap, cached by max_age); modes enforce / testing / none; mx patterns checked against the host we reach.
- F8-2 DANE (RFC 7672): TLSA at _25._tcp.<mx-host>, valid ONLY if the answer is DNSSEC-validated: needs hickory-resolver feature dnssec-ring (Cargo change) and a proof against a real signed domain before it is trusted; usages 3 and 2 with selector / matching type per the RFC.
- F8-3 TLS-RPT (RFC 8460): count successes and failures per recipient domain and policy from our real sends (new SQL counters, append-only), build the daily JSON report with the mail-auth tlsrpt structs, send it to the rua address in the domain's `_smtp._tls` TXT through our own send path.
- F8-4 "send only if TLS": a per-domain requirement derived from MTA-STS enforce or DANE, applied in the send path (fail closed: the mail waits in the Outbox with the reason, never goes out in clear), plus a global switch; loosening it needs a fresh passkey touch (the one-way policy ratchet pattern of E175).
- SQL for Qtls takes the numbers after E190 (E191 onward), strictly in order, one per file.
