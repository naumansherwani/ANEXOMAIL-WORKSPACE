THE MINDSET (every Claude, every phase): we are building the system the company will run on when it is big (Zendesk, Salesforce, Stripe-class and beyond), and a system is built ONCE. Today's small numbers (one company, zero shifts, zero cases) are NOT a reason to ship a thin or "not measured" version. They are the reason the structure must already be complete, so when the business expands the data simply flows in and nothing is rebuilt.
RULES:
1. NEVER write "Not measured", "Not measured yet", "later", "coming soon" or a placeholder instead of a real signal. If a signal is needed, DESIGN it from the real source tables (read the live schema snapshot docs/cursor-work/live-snapshot/sql/schema-public.sql and the E-series), WEB-SEARCH how the world's best systems do it, and BUILD it complete: the real computation, the closed list of values, the selftest on synthetic rows, the screen.
2. A signal that is zero today shows a real ZERO ("0 companies in grace period"), computed from the real tables. Zero is data. "Not measured" is an excuse.
3. Structure for scale: closed lists and registries (so a new plan, region, signal or queue is a data row, not a code change), append-only hash-chained series, aggregate-only doors, indexes and BRIN for millions of rows, advisory-lock samplers, forced RLS, least privilege. Write it as if the table had 100 million rows and 10,000 staff.
4. If a source table truly does not exist yet in the awam database (and cannot be derived), the phase is NOT left half: write the contract and the SQL against the reserved source (to_regclass guard so it turns on the day the table appears), the selftest with synthetic rows, and record the reserved source in the blueprint as a FUTURE-PROOF PHASE. The screen shows the real zero, never an apology.
5. Every phase plan lists in its research table what the world's best systems do, and which of those points are built NOW and which are built-in-structure for expansion.
