## WEB RESEARCH 23 Nov 2026 00:3x PKT (his order 00:25: "web research ker ke points nikal ke likho aur DBSC advance level likho")
Sources read: W3C DBSC Editor's Draft 9 Nov 2026 (w3c.github.io/webappsec-dbsc), developer.chrome.com DBSC guide, Chrome blog "second origin trial" (Chrome 142, Oct 2025 to Feb 2026, Windows + TPM first), Google security blog.
Facts that CHANGE the plan (my first draft assumed otherwise; corrected in the rows above and below):
1. Registration proof: header `typ: dbsc+jwt`, `alg` ES256 (or RS256 / none), the public key is the `jwk` in the HEADER (absent on refresh); payload `jti` = copy of our challenge. The spec defines NO iat/aud/sub; we do not rely on them. Our freshness comes from our own signed challenge (60 s, single use, bound to owner + session).
2. Headers use the `Secure-Session-` prefix: `Secure-Session-Registration` (response), `Secure-Session-Response` (request proof), `Secure-Session-Challenge: "<c>";id="<session id>"` (response, may carry several), `Sec-Secure-Session-Id` (request), `Secure-Session-Skipped` (request, reasons unreachable / server_error / quota_exceeded). Challenge step answers 403 (not 401).
3. Session JSON: `session_identifier`, `refresh_url`, `continue` (false ends the session), `scope {origin, include_site (REQUIRED boolean), scope_specification[]}`, `credentials [{type:"cookie", name, attributes}]`, `allowed_refresh_initiators`.
4. Status handling by the browser: 4xx other than 403/407/429 on refresh = the browser TERMINATES the session; 5xx = backoff only. So our doors must never answer 4xx for a transient database problem (use 503).
5. Recommended hardening for the refresh endpoint: require `Sec-Secure-Session-Id`, never send `Access-Control-Allow-Credentials`, forbid framing (X-Frame-Options / CORP), short-lived challenges, reject stale ones.
6. Per-session NEW key; no stable device id (privacy); clearing site data clears the key; a key-holding attacker with temporary device access can still sign (honest limit). Chrome falls back to the long-lived cookie when TPM busy / unreachable: keep ONE long-lived session token (our existing 12 h token) as the fallback and say so on the status door.
7. Support today: Chromium (Chrome/Edge) with TPM-backed keys; Firefox/Safari not. Same honest limit as the founder side.
